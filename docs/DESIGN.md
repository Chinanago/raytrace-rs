# グランドデザイン

raytrace-rs が目指す姿と、そこへ向かうための設計指針です。新しい機能や構成の変更は、この文書の原則と層の規則に沿って判断します。原則を変える必要が出たときは、コードより先にこの文書を更新し、[決定の記録](#14-決定の記録)に理由を残します。

現在の機能と使い方は [機能と対応範囲](FEATURES.md)・[操作ガイド](GUIDE.md)、ビルドと検証は [開発と検証](DEVELOPMENT.md) にあります。この文書は「どうあるべきか」を扱い、現状との差は [6章](#6-現状との差)と [13章](#13-移行計画) で管理します。

## 1. ビジョン

**GUIからもAIエージェントからも同じように扱える、軽量で信頼できる、オープンな光学設計・解析ソフトウェア。** 機能の到達点は、エージェントによるコマンドの組み合わせも含めて Zemax OpticStudio に相当する範囲です。アプリに持たせる機能はP12の基準で選びます。

- 人はGUIで光学系を組み立て、目で確かめながら設計します。
- エージェントは同じ光学系を同じ操作で読み、編集し、計算し、結果を解釈します。GUIの裏で動くエージェントの操作を、人がその場で見ることもできます。
- 計算結果は、入力と版が同じなら必ず同じになり、何から計算したかを辿れます。
- 単体の小さな実行ファイルで動き、GUIなしでも全機能を使えます。Webブラウザでも同じ中核が動きます。

### 機能の到達範囲

Zemax OpticStudio の機能分野ごとの対応状況と、結像系・照明系を並べた取り組みの順番は [機能マップ](CAPABILITIES.md) にあります。

段階的に広げます。構成は最初から最後の段階まで受け止められる形にします。

| 段階 | 範囲 |
|---|---|
| 現在 | 逐次・非逐次の幾何光線追跡、ZMX・AGF・STEPの取り込み、組立、スクリーンの光量分布、走査・収束確認 |
| 次 | 骨組みの再建（[13章](#13-移行計画)）、逐次系の標準解析（スポット図、光線収差図、波面・OPD）、解析の登録制、文書の木構造化、Webブラウザで動く版（WASM） |
| その先 | 最適化（変数・評価関数）、公差解析、MTF・PSF（回折計算）、偏光 |

## 2. 品質特性

設計上の判断で迷ったら、上の行を優先します。

| 優先 | 品質特性 | 具体的な基準 |
|---|---|---|
| 1 | 正しさ・再現性 | 同じ入力・同じ版で同じ結果（ビット単位）。解析解・他ソフト・物理的性質で検証済み。結果に出所の記録がある |
| 2 | 操作の対等性 | GUI・CLI・MCPで、できることが同じ。同じコマンドを同じ引数で呼ぶ |
| 3 | 堅牢性 | 不正な入力・壊れたファイル・中止でも落ちない。失敗した操作は文書を変えない |
| 4 | 軽さ・移植性 | GUIなしで完結する。依存が少ない。静的リンクの単体バイナリで動く。L0〜L4はWASMでも動く |
| 5 | 拡張性 | 面の種類・光源・解析・ファイル形式を、既存のコードに手を入れずに足せる |
| 6 | 相互運用 | ZMX・AGF・STEPを読み書きできる。外部形式の都合が内部モデルに入り込まない |
| 7 | 性能 | 大量光線を高速に追跡する。ただし1〜3を犠牲にしない |

## 3. 設計原則

| # | 原則 | 意味 | 根拠 |
|---|---|---|---|
| P1 | 文書が唯一の正 | 光学系の状態は文書だけが持つ。解析結果・表示・キャッシュは文書から再計算できる派生物 | 光学CAD・CADに共通する文書と解析の分離。コマンドとクエリの分離（CQS） |
| P2 | すべての操作はコマンド | GUI・CLI・MCP・スクリプトは、同じコマンドを `Session::execute(id, params)` で呼ぶ。ダイアログは引数を作る入力欄にすぎない | コマンドパターン。SolidCraft の「Everything is a command」 |
| P3 | 計算は純粋 | 計算の段は副作用を持たない関数。ファイル・時刻・スレッド・中止は外側が渡す | Functional core, imperative shell（Bernhardt） |
| P4 | 依存は内向き、機械で検査 | 下の層は上の層を知らない。違反はCIで落とす | 層構造（POSA）、クリーンアーキテクチャ、SolidCraft の `xtask layers` |
| P5 | 契約はスキーマ | コマンドの入出力、文書、計算記録はJSONスキーマを持ち、未知のフィールドは拒否する。スキーマは生成し、コミットし、古さをテストで検出する | 契約による設計。LSP・MCPのスキーマ駆動 |
| P6 | 外部形式は境界で変換 | ZMX・STEPなどの概念は入出力層で内部モデルに変換し、中核に持ち込まない | 腐敗防止層（Evans『DDD』）、情報隠蔽（Parnas） |
| P7 | 決定性と出所 | 乱数はseedで固定し、集計順を固定する。高速化した経路は基準経路と全結果が一致することをテストする。計算記録は文書のハッシュ・版・条件を持つ | 科学計算の再現性 |
| P8 | 落ちない | 製品コードで `unwrap`・`expect`・`panic`・`unreachable!`・assert系マクロを使わない。入力は敵対的と想定する。変更コマンドは成功するまで文書を変えない | 堅牢性。SolidCraft の hostile input 方針 |
| P9 | 拡張は登録で | 面形状・光源・解析・取り込み形式は、登録表に足すだけで全フロントエンドに現れる | 開放閉鎖原則 |
| P10 | 軽さを守る | 重い依存は最上層（GUI）に閉じ込める。中核は数個の基本的なクレートだけに依存する | 軽量性の要求 |
| P11 | 検証は設計の一部 | 新しい計算には、解析解・性質・参照結果のいずれかによる検証を同時に入れる | 検証と妥当性確認（Oberkampf & Roy） |
| P12 | 領分を守る | アプリに入れるのは、エージェントがコマンドの組み合わせでは正しく・十分速く実現できないものだけ。内部の状態や光線単位のデータへのアクセス、内側のループの速度、決定性の保証が必要な評価を提供し、最適化・公差解析・軸合わせなどの戦略はエージェント側に置く | P2・P3・P7・P10を機能の範囲にも適用し、アプリの肥大化を防ぐ |

### アプリとエージェントの領分

アプリは、速く・決定的で・純粋な評価を、型とスキーマを持つコマンドから提供します。エージェントはそれを組み合わせて、変数や評価関数の選択、探索方法、公差の割り当て、軸合わせの手順を決めます。新しい機能をアプリに足すときは、既存のコマンドでは満たせない正しさ・速度・決定性の要件を示します。内部データへのアクセスが必要な処理も、必要な評価をアプリから提供し、戦略は外に置きます。

P1が対象にするのは、現在の光学モデルの状態です。文書がどう作られたかという経緯の継続的な管理は、gitやエージェントの作業ログなどで行います。再計算やZMXへの書出しに必要な出所は文書に保持し、`session.log` はセッション内の操作を再現するために使います。

## 4. 全体構成

### 層

```
L5  フロントエンド   GUI(egui) ・ MCP ・ CLI           ← 人とエージェントの入口
L4  エンジン         セッション・コマンド登録・ジョブ・研究（走査など）
L3  入出力           文書形式・計算記録・ZMX/AGF/STEPの変換・書出し
L2  文書             設計文書（部品と配置）・展開（コンパイル）
L1  計算核           追跡・材料と分散・コーティング・光源生成・解析
L0  基礎             数学・幾何・サンプリング
```

| 規則 | 内容 |
|---|---|
| 依存の向き | 上の層は下の層を使ってよい。逆は禁止。同じ層の中でも循環は禁止 |
| UIの隔離 | egui・eframe・wgpu・rfd などGUIの依存はL5のGUIクレートだけが使う |
| 入出力の隔離 | ファイル・ネットワーク・時刻・環境変数・プロセスはL3以上で扱う。L0〜L2は純粋（L0〜L1の `raytrace-core` は `std::fs`・`std::time`・`std::env`・`std::net`・`std::process` を使わない） |
| WASM | L0〜L4は `wasm32-unknown-unknown` でビルドできる。プラットフォーム固有の処理（ファイル選択、スレッド、時刻）はL3以上の差し替え可能な部分に閉じ込める。WASMでスレッドが使えない場合も、計算核は同じ結果を返す（並列度だけが変わる） |
| 並列化 | スレッドプールはL4が用意し、L1は渡された実行環境で並列に計算する |
| 検査 | 層・依存・純粋さの規則は `cargo xtask layers`、WASMのビルドは `cargo xtask wasm` で検査し、CIで実行する |

### クレートの目標配置

| 層 | クレート | 現在との関係 |
|---|---|---|
| L0〜L1 | `raytrace-core` | 現状のまま。将来、解析を `raytrace-analysis` に分けることがある |
| L2 | `raytrace-doc` | 段階2で新設済み。`Project`・`Assembly` に代わる部品（`Part`）と配置（`Occurrence`）の文書（`Design`）と展開（`Design::compile`）。ファイル・外部形式を知らない |
| L3 | `raytrace-formats`、`raytrace-io` | formats は外部形式の読み書き（文書を知らない）。io は文書形式・計算記録・書出しと、外部形式から文書への変換 |
| L4 | `raytrace-engine`（旧 `raytrace-app`。段階3で改名・再編済み） | セッション、コマンド、計算パイプライン、走査・収束確認 |
| L5 | `raytrace-gui`、`raytrace-mcp`（段階5で新設済み）、`raytrace-cli`、Web版のフロントエンド（新設） | 薄いフロントエンド |
| 道具 | `xtask` | 層とWASMの検査など、開発用の作業。製品には含めない |

## 5. ドメインモデル（設計文書）

### 部品と配置の木

文書は **部品（component）と配置（occurrence）の木** です。単体のZMXも「部品が1つの文書」として同じ形で表します。

```
Design（文書）
├─ environment   単位・波長・基準媒質・追跡の設定
├─ components    部品の定義（それぞれ自分の局所座標で書く）
│   ├─ 光学部品   面・NSCオブジェクト・材料（ZMX由来や手入力）
│   ├─ 光源       発光の定義（Source Diode など）
│   ├─ 検出器     スクリーンの寸法と画素
│   └─ 形状部品   ロッドなど、寸法から面を生成する部品
├─ root          ルート部品。配置の一覧を持つ
│   └─ occurrence  部品の参照＋剛体変換（位置・回転）＋有効/無効
├─ analyses      保存しておく解析の定義（スクリーン、走査計画など）
└─ provenance    取り込み元（ファイル名・ハッシュ・原文の保管場所）
```

- **同じ部品を複数配置できます。** 定義を直すと、すべての配置に反映されます。
- **部品は入れ子にできます。** 光源とレンズを1つのユニットにまとめる、といった使い方です。
- **参照は安定したIDで行います。** 面番号や配列の添字では参照しません。エージェントが編集しても参照が崩れないようにするためです。
- **元のZMXは出所として保管します。** 計算に使う形とは分けて持ちます。

### 展開（コンパイル）

`compile(Design) -> (CompiledScene, Diagnostics)` は純粋な関数です。配置の変換を合成して全体座標の面・材料表・光源・検出器の一覧にし、検証と正規化を行います。計算核は `CompiledScene` だけを知り、文書の木を知りません。結果は文書の内容ハッシュで再利用できます。

### 文書の規則（段階2で確定）

| 項目 | 規則 |
|---|---|
| 型 | L2の `raytrace-doc` に `Design`（文書）・`Part`（部品）・`Occurrence`（配置）を置く。`Project` はなくす |
| ID | 部品と配置は文書内で一意の文字列ID（`[a-z][a-z0-9_-]*`）を持つ。新しいIDは `<種類>-<番号>`（`optic-3` など）で作り、番号は文書の `next_id` から払い出して再利用しない。面は「配置ID＋面の名前」で参照する（面の名前は部品の中で一意であることを既に検証している） |
| 部品の種類 | `system`（追跡方式・光源・検出器を含む完結した光学系）、`source`、`optic`、`rod`、`detector` |
| 部品の中身 | 局所座標の面・材料表と材料名・光源、取り込みの問題点、条件（未コート、単色波長）、CAD分割精度、出所 |
| 階層 | 型は入れ子を表せる形にするが、段階2で扱うのはルート直下の配置だけ |
| 展開の規則 | 配置が1つだけで、それが `system` 部品の恒等配置（移動・回転なし）のときは、部品をそのまま光学系とする。面の名前・材料表・問題点・追跡方式を変えない（単独の完結系は組み立てない）。それ以外は非逐次の組立として合成する（面の名前に配置の番号と名前を付け、材料表を統合し、光源と瞳を配置の変換で動かす）。逐次の追跡は前者の場合だけ |
| 恒等配置 | 移動・回転のない配置は座標を変換しない。変換で丸め誤差を入れないため |
| 出所 | 元のZMXなどは、形式名とJSON値として不透明に保管する。L2は中身を解釈せず、L3の入出力が型に変換して使う（ZMXの書出しなど） |
| 保存形式 | `raytrace-design-v1`。読み込みは `.zmx`・`raytrace-design-v1`・光学系だけのJSON（`examples/*.json`）に限る。ベータ期間は旧形式からの移行を持たず、旧プロジェクト形式（`raytrace-project-v1`〜`v3`）は「未対応のファイル形式」として拒否する。計算記録はいまのサンプリング版だけを再生する |

### パラメーター（その先の段階）

寸法や位置を名前付きの変数と式で表せるようにします。走査の連動条件、最適化の変数、公差の摂動は、どれも「変数に値を入れて展開し直す」ことで表せます。

## 6. 現状との差

| 目指す姿 | 現状（v0.11系） |
|---|---|
| 文書が唯一の正（P1） | 段階2で実現済み。文書は `Design` だけで、`Scene` は展開結果（`Compiled`）という派生物。GUIは文書を持たず、セッションの版が変わるたびに展開し直す（段階4）。残る差：計算記録が文書全体を含む |
| 部品と配置の木 | 段階2で実現済み。単体のZMX・JSONも1部品の文書で、恒等配置の単体系はそのまま追跡する。残る差：部品の入れ子と解析の定義（`analyses`）の保存は未実装で、ルート直下の配置だけを扱う。GUIの単体系と組立の編集画面は別のまま |
| 安定したID | 段階2で実現済み。部品・配置は文書内で一意のID、走査の対象は配置IDと面の名前で参照する（単体系は配置IDを省略できる）。残る差：GUIの選択状態は配置の添字で持つ |
| すべての操作はコマンド（P2） | 段階3・4で実現済み。計算・読込・保存・文書の編集は、`raytrace_engine` の登録表にあるコマンド（`analysis.trace`、`doc.set`、`component.add` など30個。解析も `analysis.<id>` コマンド）で、CLIとGUIが `Session` を通して呼ぶ。`engine::Request` は廃止した。GUIの編集はすべて `doc.set`・`doc.new`・`component.*`・`session.undo`/`redo` で、GUIが文書を直接書き換える箇所はない。段階5でMCPサーバー（`raytrace-mcp`、`raytrace-rs mcp`）を足し、エージェントも同じコマンドを `Session` に対して呼ぶ。残る差：起動中のGUIへ接続する方式（制御チャネル）は未実装 |
| セッション | 段階3で実現済み。`Session` が開いた文書（共有参照）・版番号・取り消し/やり直しの履歴・AGFカタログを持つ。変更は新しい文書を作って検証してから確定し、失敗は何も変えない。`run -` の流れは1つのセッション。段階4で、取り消しの単位（`group`）・履歴の上限・変更の記録（`session.log`）をセッションが持つようにし、GUI独自の履歴をなくした。GUIはUIスレッドの `Session` を1つ使う。段階5で、MCPサーバーが作業スレッドでセッションのコマンドを順に実行し、進捗と中止を通知で扱うようにした。残る差：IDで扱うジョブ、展開結果のキャッシュ |
| MCP（エージェントの入口） | 段階5で実現済み（窓なしの方式）。`raytrace-mcp`（L5）が `raytrace-rs mcp` で標準入出力のJSON-RPCを処理し、`list_commands`・`describe_command`・`execute`・`batch` の4ツールでセッションのコマンドを呼ぶ。コマンドを登録に足すと自動でMCPにも現れる。残る差：起動中のGUIへつなぐ方式（制御チャネル）、読み書きできるフォルダーの限定、引数の検査の強さの選択 |
| 計算は1本のパイプライン（P3） | 段階1で実現済み。上書き・上限・発射の確定・追跡・記録・解析の各段が `raytrace_engine::pipeline`（`crates/raytrace-engine/src/pipeline.rs`）にあり、`engine/run.rs`・`scan.rs`・`convergence.rs` が共有する。`record.rs` から追跡を除いた |
| 解析は登録制（P9） | 段階6で実現済み。`raytrace_engine::analysis` に `Analysis`（ID・要約・設定の型・結果の型・`run(&RunView, 設定)`）の登録表があり、登録すると `analysis.<id>` コマンド（問い合わせ）になる。`analysis.budget`（光量収支）と `analysis.screen`（スクリーンの受光・ピーク・断面・半値幅・ROI）があり、GUIのスクリーン画面は `analysis.screen` の結果を描く。セッションは直近の計算記録（`analysis.trace`・`run.replay`・`run.open`）を1件保持し、`run` を省略した解析はそれを使う。残る差：逐次系の標準解析（スポット図など）は未実装で、`doc.inspect` の互換性レポートは解析の登録表に入っていない |
| 外部形式は境界で変換（P6） | 元のZMXは部品の出所として不透明なJSONで保管し、L2はその中身を解釈しない。取り込みの問題点は部品が持つ。残る差：計算記録が文書全体を含む（含めるかの選択式は未実装） |
| 層の自動検査（P4） | 実現済み。`cargo xtask layers` が層の順序・GUI依存の隔離・計算核の純粋さを、`cargo xtask wasm` がL0〜L4のWASMビルドをCIで検査する |
| 落ちない（P8） | 段階6bで実現済み。workspaceのClippy lint（`unwrap_used`・`expect_used`・`panic`・`unreachable` をdeny、assert系マクロは `cargo xtask no-panic` で構文検査、`clippy.toml` でテスト内は許可）が製品コードでの使用を機械的に禁止する。既存の箇所はエラー（`Error::Internal` を含む）または非パニックの書き方に直し、型で保証される例外の `#[allow]` はない。結合テスト・examplesは先頭の `#![allow]` で許可 |
| 契約はスキーマ（P5） | 実現済み。`schemas/` を生成し、古さをテストで検出している |
| 決定性（P7） | 実現済み。集計順の固定、SIMD・BVHと基準経路の一致テストがある |

## 7. セッションとコマンド

### セッション

セッションはL4にあり、次のものを持ちます。

- 開いている文書（不変の値として持ち、変更のたびに新しい版を作る）と、その版番号
- 取り消し・やり直しの履歴
- 実行中のジョブ（ID・進捗・中止）
- 展開結果や計算結果のキャッシュ（内容ハッシュで再利用）

選択状態やカメラなどの表示の状態はGUIのものとし、文書には入れません。

### コマンド

| 項目 | 規則 |
|---|---|
| ID | `<領域>.<動作>` の小文字ドット区切り（`doc.open`、`component.move`、`analysis.trace`） |
| 契約 | 入力と出力のJSONスキーマを必ず持つ。未知のフィールドは拒否 |
| 種類 | 文書を変える「変更」と、変えない「問い合わせ」に分ける |
| 変更 | 既定で取り消し可能。成功するまで文書を変えない。`expected_revision` を付ければ、GUIとエージェントが同時に編集しても古い版への上書きを拒否できる |
| まとめて実行 | 複数の変更を1つの取り消し単位として、全部成功か全部失敗で実行できる |
| 長い計算 | ジョブとして開始し、IDで進捗・中止・結果を扱う |
| 発見 | `command.list` と `command.describe` で、コマンドの一覧とスキーマを問い合わせられる |
| 対話 | プログラムからの呼び出しはダイアログを開かない |

### コマンド体系（段階3で確定）

| 領域 | コマンド | 種類 |
|---|---|---|
| `app` | `version` | 問い合わせ |
| `command` | `list`、`describe` | 問い合わせ |
| `schema` | `get`（`name` のスキーマを返す、`output` で書き出す） | 問い合わせ |
| `doc` | `new`（空の組立、または `design` を指定して新しい文書を始める）、`open`（ZMX・設計JSON・光学系JSONを開いてセッションの文書にする）、`save`、`get`（文書を返す）、`inspect`（互換性レポート）、`export_zmx` | 変更・問い合わせ |
| `doc` | `set`（文書の1か所を書き換える）、`replace`（文書全体を置き換える） | 変更 |
| `component` | `add`（ファイルの取り込み、ロッド、スクリーン）、`remove`、`duplicate` | 変更 |
| `analysis` | `trace` | 問い合わせ（長い計算） |
| `study` | `scan`、`resume`、`convergence`、`open` | 長い計算・問い合わせ |
| `run` | `open`、`replay`、`save`、`export_screen` | 問い合わせ・長い計算 |
| `session` | `undo`、`redo`、`status`、`log`（変更の記録） | 変更・問い合わせ |

| 項目 | 決定 |
|---|---|
| 編集の汎用コマンド | `doc.set {path, value}` は文書の1か所をJSON Pointerで指定して書き換える。配列の要素は添字のほか `@<ID>`（`/occurrences/@rod-4/pose/translation_mm/2`）で指定できる。書き換え後の文書をスキーマどおりに読み直し、展開できることを確かめてから確定する。こうすると、文書のスキーマに載っている項目はすべて、専用コマンドを足さずに編集できる |
| 構造の変更 | 部品の追加・削除・複製のように、IDの払い出しや関連の整理が要る操作は専用コマンドにする |
| 一回限りの呼び出し | 文書を使うコマンドは `model`（パス・設計・光学系）を省略できる。省略するとセッションの文書を使い、なければ `no_document` で失敗する。`model` を渡すと、そのモデルだけを扱い、セッションは変えない。CLIの1回の呼び出しは新しいセッションなので従来どおり `model` を渡す。`run` で続けて渡したリクエストは1つのセッションを共有する |
| 取り消し | 変更コマンドの前に文書を丸ごと保持する（文書は共有参照で持つので複製は安い）。失敗した変更は文書も履歴も変えない |
| 版番号 | 変更が確定するたびに1増える。取り消し・やり直し・文書を開く操作でも1増える（減らさないので、同じ版番号が別の内容を指すことはない）。変更コマンドは `expected_revision` を受け付け、一致しなければ `revision` エラーで拒否する。応答の `revision` は、コマンド実行後のセッションの版番号 |
| ジョブ | 段階3では、長い計算は呼び出し側のスレッドで同期的に実行し、中止と進捗は制御オブジェクトで渡す（GUIは作業スレッドから呼ぶ）。段階5のMCPサーバーも同じ方式で、受け取った呼び出しを作業スレッドが1つずつ実行し、入力の読み取りは止めない（中止は呼び出しごとの制御オブジェクト、進捗は通知）。IDで扱う非同期ジョブは、必要になった時点で入れる |
| スキーマ | 各コマンドは入力と出力のスキーマを持つ。`schema.get name=request`・`response` はコマンド登録から生成する（`command` で分岐し、各コマンドの入力・結果を並べる） |
| クレート | `raytrace-app` を `raytrace-engine` に改名し、セッションとコマンド登録を置く（段階3で実施済み） |

### GUIの編集（段階4で確定）

| 項目 | 決定 |
|---|---|
| 文書の持ち主 | GUIはUIスレッドに `Session` を1つ持ち、文書はセッションだけが持つ。GUIは描画のたびにセッションの文書（共有参照）を読む。計算は文書の共有参照を作業スレッドへ渡して実行する |
| 編集 | GUIの編集はすべて `doc.set`・`component.*`・`session.undo`/`redo` で行う。GUIが文書を直接書き換える箇所をなくす |
| 編集のまとまり | 変更コマンドは任意の `group`（文字列）を受け付ける。直前の変更と同じ `group` の変更は、取り消しの1単位にまとめる。GUIはドラッグや1つの入力欄の連続した編集に同じ `group` を付け、確定したら別の値に変える。エージェントも同じ方法で編集をまとめられる |
| 履歴の上限 | 取り消しの上限（64操作、文書の推定サイズ約128 MiB）はセッションが持つ（`HistoryLimits`）。古い操作から捨て、最新の1操作は必ず残す。GUI独自の履歴はなくした。上限を超えて捨てた操作も `session.log` には残る |
| 操作の記録 | セッションは確定した変更コマンド（コマンドIDと引数のJSON）を順に記録し、`session.log` で返す。取り消された変更は記録から外す。記録を新しいセッションで同じ順に実行すると同じ文書になる。GUIの編集をエージェントが再現・監査できるようにするため |
| `group` を受け付けるコマンド | 取り消し可能な1回の変更を作る `doc.set`・`doc.replace`・`component.add`・`component.remove`・`component.duplicate`。文書を開く・作る `doc.new`・`doc.open` は履歴を始め直し、`session.undo`/`redo` は履歴を進めるので `group` を持たない。`group` を持つ変更が直前の変更と同じ `group` で、間に取り消し・やり直し・文書を開く操作がなければ、取り消しの1単位にまとめる（取り消しは最初の変更の前の状態に戻る）。版番号は変更ごとに1増える |
| `session.log` の形 | `{revision, base, entries}`。`base` は文書を始めた `doc.open`・`doc.new`（`doc.replace` で始めたセッションでは `null`）、`entries` はその後に確定した変更を古い順に並べた `{command, params}`。`params` は実行したパラメーターで、`expected_revision` は含めない。`base` を実行してから `entries` を順に実行すると同じ文書になる。取り消した変更は外れ、やり直すと戻り、取り消し後の新しい変更はやり直せる変更を捨てる。同じ `group` の中で同じ `path` を書き換える連続した `doc.set` は最後の1件にまとめる（ドラッグが1件になる）。履歴の上限で捨てた操作も記録には残る。ライブラリから `Session::edit`・`Session::replace` を直接呼ぶ場合は、コマンドを経由しないので記録されない |
| `doc.new` と保存状態 | `doc.new` は `design` で開始する文書を指定できる（GUIのサンプルや計算記録の文書。`base` に文書全体が入る）。開いた・作った文書は、保存していなくても未保存の変更なしとして始まる（変更があると `dirty`）。`doc.replace` で始めたセッションは未保存扱い |
| 別スレッドでの読込 | ファイルの読込は作業スレッドで行う。GUIは新しい `Session` に `doc.open` を実行させるか、UIのセッションの複製（`Session` は `Clone`）に `component.add` を実行させ、終わったら `Session::adopt` で取り込む。履歴・記録・版番号（増え続ける）を引き継ぐ。読込の間は編集操作を無効にする |
| GUIの編集の流れ | 部品のウィジェットは、いま見ている部品の小さな作業コピー（姿勢、ロッド、光源の一覧など）を編集する。描画のあと、コピーと文書をJSONで比べ、異なる値ごとに1つの `doc.set` を実行する（変更は `group` を持つ）。ドラッグやひとつの入力欄の連続した入力は、マウスを離す・入力欄を離れるまで同じ `group`（`gui:<番号>`）で、そこで番号を進める。構造の変更（追加・削除・複製）は `group` なしで、ロッド・スクリーンの追加とその位置の設定だけ同じ `group` にして1操作にする |
| 計算結果の鮮度 | 計算結果は計算した文書の共有参照を持ち、セッションの文書がその参照と同じ間は最新とみなす。取り消しで計算時の文書に戻ると、その結果の光路を再び表示する（版番号は戻らないので、版番号では比べない）。光線数の上限の切り替えは文書の変更ではないので、結果が持つ上限と比べる |
| 選択状態 | 選択中の部品・面・光源はGUIが持ち、離れた文書ごとに覚えて、取り消し・やり直しで戻す。光線数の上限の切り替えは取り消しの対象にしない |

## 8. 計算パイプライン

```
Design ─compile→ CompiledScene ─configure→ CompiledScene' ─prepare→ PreparedScene
                                                                         │
     解析結果 ←analyze─ Report ←accumulate─ 光線ごとの結果 ←trace─ launch ─┘
```

- 各段は純粋な関数で、入出力は型付きの成果物です。前後の段の中身を知りません。
- 単発の追跡・走査・収束確認・再計算・GUIのプレビューは、**同じ段の組み合わせ方の違い**として書きます。独自の追跡ループを持ちません。
- 走査は文書の変数を変えて展開以降をやり直します。最適化・公差解析・軸合わせの戦略はエージェントがコマンドを組み合わせて実行し、アプリは同じパイプラインによる評価を返します（P12）。展開結果はキャッシュで再利用します。
- 中止と進捗は外から渡す制御オブジェクトで扱います。
- 決定性の規則（P7）はこのパイプライン全体で守ります。並列化しても固定の区切りと順序で集計します。

## 9. 解析

解析は登録制の純粋関数です。

```
Analysis { id, 設定のスキーマ, 結果のスキーマ, run(CompiledScene, Report/Run, 設定) -> 結果 }
```

- 解析を登録すると、`analysis.<id>` コマンド、MCPのツール、CLIの引数、スキーマが自動で揃います。
- GUIは結果を描くだけで、計算を自分で持ちません（表示のための補間などは除きます）。
- 現在の候補は、光量収支、スクリーン分布、断面と半値幅、ROI、互換性レポートです。次の段階でスポット図、光線収差図、OPDを足します。

### 解析の登録制（段階6で確定）

| 項目 | 決定 |
|---|---|
| 登録 | エンジンに解析の登録表を置く。1つの解析は ID・要約・設定の型・結果の型・関数 `run(&RunView, 設定) -> 結果` を持ち、登録すると `analysis.<id>` コマンドになる（入出力スキーマ、CLI、MCP、`command.list` に自動で現れる） |
| 計算の置き場所 | 解析の数値計算そのものは純粋関数として下の層（`raytrace-core` のスクリーン解析など）に置き、登録はその関数を呼ぶだけにする |
| 入力の計算記録 | 解析は `run`（計算記録のパスかインライン）を受け取る。省略すると、セッションが保持する直近の計算結果（`analysis.trace`・`run.replay`・`run.open` の結果）を使う。直近の結果がなければ `no_run` エラー。直近の結果には、それを計算した文書の版番号を付けて返し、文書が変わったあとなら `stale: true` を示す |
| 最初の解析 | `analysis.budget`（光量収支の割合、収支誤差、未解決分）、`analysis.screen`（スクリーンの画素寸法・ピーク・X/Y断面と半値幅・ROIの積分。断面位置とROIは設定で指定）。互換性レポートは文書の解析なので `doc.inspect` のまま |
| GUI | スクリーンの断面・半値幅・ROIは `analysis.screen` の結果を描く。色付けや補間など表示だけの処理はGUIに残す |

### 落ちない規則の機械的な検査（段階6で確定）

製品コードでの `unwrap`・`expect`・`panic!` は、workspaceのClippy lint（`unwrap_used`・`expect_used`・`panic` を deny、テストでは許可）で禁止する。既存の箇所はエラーを返す形に直す。型の上で起こりえない場合に限り、理由を書いた `#[allow]` を個別に付けてよい。テスト（`#[cfg(test)]`・`#[test]`）は `clippy.toml` の `allow-*-in-tests` で、結合テスト（`tests/`）とexamplesはファイル先頭の `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::panic)]` で許可する。不変条件が破れたときの `raytrace_core::Error::Internal`（コード `internal`）を用意し、`trace`・`trace_controlled` は `Result` を返す。

## 10. 入出力と形式

| 対象 | 方針 |
|---|---|
| 設計文書 | 版付きのJSON（スキーマあり）。書き出しは最新の版だけ。1.0までのベータ期間は旧版を読まない。移行処理は1.0から持ち、版を上げるときは移行処理とテストを同時に足す |
| 計算記録 | 計算に使った `CompiledScene`・発射条件・追跡条件・版・文書のハッシュを持つ。これだけで再計算できる。文書そのものを含めるかは選択式にする |
| 外部形式の取り込み | ZMX・AGF・STEPは部品として取り込み、出所を記録する。対応しない定義は互換性レポートで明示し、黙って捨てない |
| 書出し | ZMX、スクリーンのCSV・PNG。外部形式で表せない内容は書き出せないことを明示する |
| 利用者のデータ | ZMX・STEP・計算記録はリポジトリに含めない（既存の公開物チェックを維持） |

## 11. フロントエンド

| 入口 | 役割 |
|---|---|
| GUI | セッションの状態を読んで描き、操作はすべてコマンドで送る。ダイアログはコマンドの引数を作るだけ。描画・カメラ・選択はGUIの責任 |
| MCP | 標準入出力のJSON-RPC。窓なしでセッションを持って動く方式と、起動中のGUIにローカルの制御チャネル（そのつど作るトークン付き）でつなぐ方式を持つ。後者では、人がGUIでエージェントの操作を見られる。引数の検査は「なし・警告・拒否」を選べる |
| CLI | 窓なしのセッションの薄い殻。`raytrace-rs COMMAND field=値` と `run REQUEST.json` で、MCPと同じコマンドを1回ずつ実行する。独自のオプションは持たない |
| スキル・AGENTS.md | エージェントへの案内。コマンドの詳細はスキーマと `command.describe` を正とし、文書に重複して書かない |

### MCPサーバー（段階5で確定）

| 項目 | 決定 |
|---|---|
| クレートと起動 | L5の `raytrace-mcp` に置き、`raytrace-rs mcp` で起動する。外部のMCPライブラリには依存せず、標準入出力のJSON-RPC 2.0（1行1メッセージ）を自前で処理する。対応するプロトコルの版は 2025-06-18、2025-03-26、2024-11-05 |
| セッション | サーバーのプロセスごとにセッションを1つ持つ。エージェントは開いた文書を続けて編集・計算できる。起動中のGUIへ接続する方式（制御チャネル）は後の段階で足す |
| ツール | コマンドごとのツールにはしない。設計文書のスキーマ（数十KB）が多くのツール定義に埋め込まれ、エージェントの文脈を圧迫するため。ツールは `list_commands`（ID・種類・要約の一覧）、`describe_command`（1つのコマンドの入出力スキーマ）、`execute`（`command` と `params` で1つのコマンドを実行）、`batch`（複数のコマンドを順に実行し、最初の失敗で止める）の4つ。コマンドを足すと自動でMCPからも使える |
| 結果 | 成功時はCLIと同じ応答（`ok`・`command`・`revision`・`result`）を構造化内容とテキストの両方で返す。コマンドの失敗はツールの結果として `isError: true` と `error.code`・`error.message` を返し、JSON-RPCのエラーはプロトコルの誤りだけに使う |
| 進捗と中止 | 長い計算は作業スレッドで実行し、入力の読み取りは止めない。依頼に `progressToken` があれば走査の進捗を `notifications/progress` で送る。`notifications/cancelled` を受けたら制御オブジェクトで計算を中止する |
| ファイル | MCPサーバーはCLIと同じく、起動した利用者の権限でファイルを読み書きする。読み書きできるフォルダーを限定する仕組みは後の段階で検討する |
| 実装の細目 | 段階5で実装済み（`crates/raytrace-mcp`）。`initialize` の前のリクエストも受け付ける（寛容）。JSON-RPCのバッチ（配列）は拒否する（`-32600`）。1行は64 MiBまで。`list_commands`・`describe_command`・`ping`・`notifications/cancelled` は読み取りの側で即座に答え、`execute`・`batch` は作業スレッドの待ち行列に入れて順に実行する。中止は呼び出しごとの `TraceControl.cancel` を立てる（始まっていない呼び出しは実行せず `cancelled` で答える。通知を受けた呼び出しにも結果は返す）。進捗は走査が終えたケース数、単独の追跡が処理した光線数（250 msごとに取得）で、`batch` では「実行中の要求の番号＋その進み具合」に対する要求数として単調に増やす。`outputSchema` は 2025-06-18 のときだけ付ける。標準入力が閉じたら、受け取った呼び出しを終えて終了コード0で終わる。作業スレッドの異常（パニック）は、その呼び出しの `internal` エラーにとどめ、サーバーは続ける |

## 12. 信頼性と検証

| 段階 | 内容 |
|---|---|
| 単体・性質 | Snell則、Fresnel、エネルギー保存、座標変換で結果が変わらないこと、seedによる再現 |
| 解析解 | 平板・球面・ロッドなど、手で導ける値との一致 |
| 参照結果 | 自作データの固定結果（STEPの900本の光線など）と、全レポートの一致 |
| 経路の一致 | SIMD・BVH・小分け生成と基準経路の全結果の一致 |
| 他ソフトとの照合 | OpticStudio との照合（継続課題）を、条件と許容差つきで記録する |
| 堅牢性 | 不正な入力・壊れたファイルでも落ちないことの回帰テスト。`fuzz/` のZMX・AGF・STEPターゲットをAddressSanitizer付きで各30秒CI実行（[手順](../fuzz/README.md)）。有限時間の検査は無欠陥の証明ではない |
| CIの関門 | 整形、Clippy、層の検査、スキーマの鮮度、公開物チェック、全テスト、配布物の動作確認 |

## 13. 移行計画

一度に作り直さず、新しい構造で古い部分を順に置き換えます（絞め殺しのイチジク方式）。各段階の終わりで全テストとCIが通る状態を保ちます。

| 段階 | 内容 | 完了の条件 |
|---|---|---|
| 0 | この文書を設計指針として採用する。`cargo xtask layers`（層・依存・純粋さ）と `cargo xtask wasm`（L0〜L4のWASMビルド）をCIに入れる | 違反がCIで検出される |
| 1 | 計算パイプラインを1本にする。展開〜記録の段を純粋関数として切り出し、エンジン・走査・収束確認・再計算をそれに乗せる。外部仕様は変えない | 追跡ループが1か所だけになり、既存のテストがすべて通る |
| 2 | 設計文書を部品と配置の木にし、安定したIDを導入する（`raytrace-doc`）。単体のZMXも部品1つの文書にする。過去のプロジェクト形式（v1〜v3）は段階2で読み込み時に移行していたが、ベータ期間の方針（14章）により廃止した | GUIと計算が新しい文書だけを使う |
| 3 | セッションとコマンド登録をエンジンに入れる（`raytrace-engine`）。取り消し・版番号・ジョブ・`command.describe` を持たせ、CLIをその上に載せる | `engine::Request` がコマンド体系に置き換わる |
| 4 | GUIの編集をすべてコマンド経由にする。GUIが文書を直接書き換える箇所をなくす | GUIで行った編集を、同じコマンド列で再現できる |
| 5 | MCPサーバー（`raytrace-mcp`）を足す。窓なしの方式と、GUIへ接続する方式を持つ。**窓なしの方式は実施済み**（GUIへ接続する方式は後の段階） | エージェントがGUIと同じ操作で設計・計算・解析を行える |
| 6 | 解析の登録制を広げ、検証を体系化する。製品コードから `unwrap`・`expect` をなくす。**解析の登録制は実施済み**（6a：`analysis.budget`・`analysis.screen`、GUIの移行）。**6bも実施済み**（`unwrap`・`expect`・`panic!` をClippyでdeny）。段階6は完了 | 解析を足すときに中核以外を変えずに済む |
| 7 | Web版。L4のセッションをブラウザで動かし、WASM向けのフロントエンドから同じコマンドを使う。スレッドなしでも同じ結果になることをテストする | ブラウザでサンプルを開いて追跡・表示できる |
| 8以降 | 逐次系の標準解析、パラメーター、最適化・公差解析に必要な評価、回折・偏光。戦略はエージェント側に置く（P12） | [1章](#機能の到達範囲) の段階に従う |

| 2026-11-08 | CLIは独自のオプションを持たず、引数をリクエストのフィールドとして組み立てる | スキーマを唯一の契約にする（P5）。オプションごとの保守をなくす |
| 2026-11-08 | 文書モデルは部品と配置の木に一本化し、単体のZMXは部品1つの文書とする | 2つの文書モデルの並存を解消する（P1） |
| 2026-11-08 | エージェントの主な入口は、セッションを持つMCPとする | 同じ系を編集しながら追い込む使い方に、一回限りの呼び出しは向かない |
| 2026-11-08 | WASM対応を次の目標に入れ、L0〜L4はWASMでビルドできることを層の規則にする | Webでも同じ中核を動かすため。規則を先に固めておくと、プラットフォーム依存が中核に入り込まない |
| 2026-11-08 | 段階2で設計文書を `raytrace-doc` に実装した。恒等配置の座標は変換しない。旧組立は恒等の回転でも姿勢角を行列から再計算していたため、符号付きゼロだけが異なる値を持つことがある（追跡結果は一致を確認）。エラーの識別子 `project` は `design` に改めた。走査の参照はID（旧 `component`・`surface` の添字をやめた）にしたため、旧形式の走査記録は再開できない | 添字参照とコピーによる組立をなくし、文書の木にIDで参照する（P1）。変換で丸め誤差を入れない |
| 2026-11-08 | 構成の参考として SolidCraft（Rust製CAD、MIT/Apache-2.0）の層構造・コマンド・セッション・MCPの考え方を取り入れる。コードは写さない | GUI・エージェント両対応のRustアプリとして実績がある構成 |
| 2026-11-08 | 段階3でセッションとコマンド登録を `raytrace-engine` に実装した。取り消し・やり直しも版番号を進める（減らさない）。ダーティ判定は保存時の文書との同一性で行う。旧 `open` は設計だけを開き、計算記録は `run_record`、走査ディレクトリは `study_directory` のエラーで各コマンドを案内する。GUIは段階3では文書を自分で持ち、操作ごとに新しい `Session` を作って `model` を渡す（セッションを共有すると、計算中に保存などの操作が待たされるため）。結果の型は `Response` に型付きで残し、JSONは `serde_json` の `raw_value` 機能で構造体の順序のまま出力する | 登録表・型付きの入口・JSONの入口を1つの関数に集め（P2）、応答の形と項目の順序を保つ。GUIの編集のコマンド化は段階4 |
| 2026-11-08 | 段階4でGUIの編集をすべてセッションのコマンド経由にした。取り消しのまとまり（`group`）、履歴の上限、変更の記録（`session.log`）をセッションに入れ、GUI独自の履歴（`gui/history.rs`）をなくした。`doc.new` に `design` を足し、開いた文書は未保存の変更なしで始まる。読込は作業スレッドのセッション（または複製）を `Session::adopt` で取り込む。光線数の上限の切り替えは取り消しの対象から外れ、ファイルを開くときに引き継ぐ計算条件（未コート・単色波長）は開いた文書への編集として記録される | 文書の持ち主と履歴を1つにし、GUIで行った編集をエージェントが同じコマンド列で再現・監査できるようにする（P1・P2）。`doc.set` は編集する部品・配置だけをJSONにするので、大きなメッシュを含む文書でもドラッグが重くならない |
| 2026-11-08 | 段階5でMCPサーバー（`raytrace-mcp`、`raytrace-rs mcp`）を実装した。外部のMCPライブラリには依存せず、ツールは4つに限る。IDで扱うジョブは入れず、1つの作業スレッドが呼び出しを順に実行する。GUIへ接続する方式は後の段階 | 設計文書のスキーマが大きく、コマンドごとのツールは文脈を圧迫するため。セッションの持ち主を作業スレッド1つにすると、取り消し・版番号の規則が変わらない |
| 2026-11-09 | 段階6bで `unwrap`・`expect`・`panic!` をworkspaceのClippy lintでdenyした。`raytrace_core::trace::trace` と `trace_controlled` は `Result` を返し、未検証の波長などで以前はパニックした箇所はエラーになる。`validation::cases()` も `Result` を返す | 落ちない（P8）を人の注意ではなく機械で守る。入力が敵対的でも計算核が落ちないようにする |
| 2026-11-09 | ベータ期間は旧形式・旧APIとの互換を持たない。コマンドの別名（`command::ALIASES`）、旧プロジェクト形式（`raytrace-project-v1`〜`v3`）の移行、旧版の計算記録（`project` フィールド、サンプリング版1/2）、旧走査記録の専用エラーを削除した | 負債を残さないため。利用者がまだ少ない |
| 2026-11-11 | P8の検査を `unreachable` のClippy denyと `cargo xtask no-panic`（製品モジュールのassert系マクロの構文検査）で補強し、残存するpanic経路をエラーにした。ZMX・AGF・STEPの独立したcargo-fuzz workspaceとCIの短時間実行を追加する | `clippy::panic` はassertとunreachableを検出しない。入力の堅牢性を実行でも検査し、ファジングの依存を製品に入れない |
| 2026-11-13 | P12「領分を守る」を追加した。アプリはコマンドの組み合わせでは満たせない評価を提供し、最適化・公差解析・軸合わせの戦略はエージェント側に置く。P1は光学モデルの状態を対象とし、文書を作った経緯はgitや作業ログで管理する。機能マップの責務分担も合わせた（[#4](https://github.com/Chinanago/raytrace-rs/issues/4)） | 軽さを依存ライブラリだけでなく機能の範囲でも守り、既存コマンドで実現できる戦略をアプリに重複実装しない |

新しい決定はこの表に追記します。原則（3章）や層（4章）を変える決定は、本文も同時に更新します。

## 16. 用語

| 用語 | 意味 |
|---|---|
| 文書（設計文書） | 光学系の唯一の正。部品・配置・環境・解析の定義・出所を持つ |
| 部品（component） | 局所座標で定義された光学系の単位。レンズ、光源、検出器、ロッドなど |
| 配置（occurrence） | 部品の参照と剛体変換。同じ部品を複数配置できる |
| 展開（compile） | 文書を全体座標の面の一覧（`CompiledScene`）に変換する純粋な処理 |
| コマンド | セッションに対する名前付きの操作。入出力のスキーマを持つ |
| セッション | 開いた文書・履歴・ジョブ・キャッシュを持つエンジンの状態 |
| 計算記録 | 1回の追跡の条件と結果。単独で再計算できる |
| 解析 | 展開結果と追跡結果から結果を計算する、登録制の純粋関数 |
