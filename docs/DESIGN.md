# グランドデザイン

raytrace-rs が目指す姿と、そこへ向かうための設計指針です。新しい機能や構成の変更は、この文書の原則と層の規則に沿って判断します。原則を変える必要が出たときは、コードより先にこの文書を更新し、[決定の記録](#14-決定の記録)に理由を残します。

現在の機能と使い方は [機能と対応範囲](FEATURES.md)・[操作ガイド](GUIDE.md)、ビルドと検証は [開発と検証](DEVELOPMENT.md) にあります。この文書は「どうあるべきか」を扱い、現状との差は [6章](#6-現状との差)と [13章](#13-移行計画) で管理します。

## 1. ビジョン

**GUIからもAIエージェントからも同じように扱える、軽量で信頼できる、オープンな光学設計・解析ソフトウェア。** 機能の到達点は Zemax OpticStudio に相当する範囲です。

- 人はGUIで光学系を組み立て、目で確かめながら設計します。
- エージェントは同じ光学系を同じ操作で読み、編集し、計算し、結果を解釈します。GUIの裏で動くエージェントの操作を、人がその場で見ることもできます。
- 計算結果は、入力と版が同じなら必ず同じになり、何から計算したかを辿れます。
- 単体の小さな実行ファイルで動き、GUIなしでも全機能を使えます。Webブラウザでも同じ中核が動きます。

### 機能の到達範囲

段階的に広げます。構成は最初から最後の段階まで受け止められる形にします。

| 段階 | 範囲 |
|---|---|
| 現在 | 逐次・非逐次の幾何光線追跡、ZMX・AGF・STEPの取り込み、組立、スクリーンの光量分布、走査・収束確認 |
| 次 | 骨組みの再建（[13章](#13-移行計画)）、逐次系の標準解析（スポット図、光線収差図、波面・OPD）、解析の登録制、文書の木構造化、Webブラウザで動く版（WASM） |
| その先 | 最適化（変数・評価関数）、公差解析、MTF・PSF（回折計算）、偏光 |

## 2. 品質特性

設計上の判断で迷ったら、上の行を優先します。

| 優先 | 品質特性 | 具体的な基準 |
|---|---|---|
| 1 | 正しさ・再現性 | 同じ入力・同じ版で同じ結果（ビット単位）。解析解・他ソフト・物理的性質で検証済み。結果に出所の記録がある |
| 2 | 操作の対等性 | GUI・CLI・MCPで、できることが同じ。同じコマンドを同じ引数で呼ぶ |
| 3 | 堅牢性 | 不正な入力・壊れたファイル・中止でも落ちない。失敗した操作は文書を変えない |
| 4 | 軽さ・移植性 | GUIなしで完結する。依存が少ない。静的リンクの単体バイナリで動く。L0〜L4はWASMでも動く |
| 5 | 拡張性 | 面の種類・光源・解析・ファイル形式を、既存のコードに手を入れずに足せる |
| 6 | 相互運用 | ZMX・AGF・STEPを読み書きできる。外部形式の都合が内部モデルに入り込まない |
| 7 | 性能 | 大量光線を高速に追跡する。ただし1〜3を犠牲にしない |

## 3. 設計原則

| # | 原則 | 意味 | 根拠 |
|---|---|---|---|
| P1 | 文書が唯一の正 | 光学系の状態は文書だけが持つ。解析結果・表示・キャッシュは文書から再計算できる派生物 | 光学CAD・CADに共通する文書と解析の分離。コマンドとクエリの分離（CQS） |
| P2 | すべての操作はコマンド | GUI・CLI・MCP・スクリプトは、同じコマンドを `Session::execute(id, params)` で呼ぶ。ダイアログは引数を作る入力欄にすぎない | コマンドパターン。SolidCraft の「Everything is a command」 |
| P3 | 計算は純粋 | 計算の段は副作用を持たない関数。ファイル・時刻・スレッド・中止は外側が渡す | Functional core, imperative shell（Bernhardt） |
| P4 | 依存は内向き、機械で検査 | 下の層は上の層を知らない。違反はCIで落とす | 層構造（POSA）、クリーンアーキテクチャ、SolidCraft の `xtask layers` |
| P5 | 契約はスキーマ | コマンドの入出力、文書、計算記録はJSONスキーマを持ち、未知のフィールドは拒否する。スキーマは生成し、コミットし、古さをテストで検出する | 契約による設計。LSP・MCPのスキーマ駆動 |
| P6 | 外部形式は境界で変換 | ZMX・STEPなどの概念は入出力層で内部モデルに変換し、中核に持ち込まない | 腐敗防止層（Evans『DDD』）、情報隠蔽（Parnas） |
| P7 | 決定性と出所 | 乱数はseedで固定し、集計順を固定する。高速化した経路は基準経路と全結果が一致することをテストする。計算記録は文書のハッシュ・版・条件を持つ | 科学計算の再現性 |
| P8 | 落ちない | 製品コードで `unwrap`・`expect`・`panic` を使わない。入力は敵対的と想定する。変更コマンドは成功するまで文書を変えない | 堅牢性。SolidCraft の hostile input 方針 |
| P9 | 拡張は登録で | 面形状・光源・解析・取り込み形式は、登録表に足すだけで全フロントエンドに現れる | 開放閉鎖原則 |
| P10 | 軽さを守る | 重い依存は最上層（GUI）に閉じ込める。中核は数個の基本的なクレートだけに依存する | 軽量性の要求 |
| P11 | 検証は設計の一部 | 新しい計算には、解析解・性質・参照結果のいずれかによる検証を同時に入れる | 検証と妥当性確認（Oberkampf & Roy） |

## 4. 全体構成

### 層

```
L5  フロントエンド   GUI(egui) ・ MCP ・ CLI           ← 人とエージェントの入口
L4  エンジン         セッション・コマンド登録・ジョブ・研究（走査など）
L3  入出力           文書形式・計算記録・ZMX/AGF/STEPの変換・書出し
L2  文書             設計文書（部品と配置）・展開（コンパイル）
L1  計算核           追跡・材料と分散・コーティング・光源生成・解析
L0  基礎             数学・幾何・サンプリング
```

| 規則 | 内容 |
|---|---|
| 依存の向き | 上の層は下の層を使ってよい。逆は禁止。同じ層の中でも循環は禁止 |
| UIの隔離 | egui・eframe・wgpu・rfd などGUIの依存はL5のGUIクレートだけが使う |
| 入出力の隔離 | ファイル・ネットワーク・時刻・環境変数・プロセスはL3以上で扱う。L0〜L2は純粋（L0〜L1の `raytrace-core` は `std::fs`・`std::time`・`std::env`・`std::net`・`std::process` を使わない） |
| WASM | L0〜L4は `wasm32-unknown-unknown` でビルドできる。プラットフォーム固有の処理（ファイル選択、スレッド、時刻）はL3以上の差し替え可能な部分に閉じ込める。WASMでスレッドが使えない場合も、計算核は同じ結果を返す（並列度だけが変わる） |
| 並列化 | スレッドプールはL4が用意し、L1は渡された実行環境で並列に計算する |
| 検査 | 層・依存・純粋さの規則は `cargo xtask layers`、WASMのビルドは `cargo xtask wasm` で検査し、CIで実行する |

### クレートの目標配置

| 層 | クレート | 現在との関係 |
|---|---|---|
| L0〜L1 | `raytrace-core` | 現状のまま。将来、解析を `raytrace-analysis` に分けることがある |
| L2 | `raytrace-doc`（新設） | `raytrace-io` の `project`・`assembly` を移し、木構造の文書にする |
| L3 | `raytrace-formats`、`raytrace-io` | formats は外部形式の読み書き（文書を知らない）。io は文書形式・計算記録・書出しと、外部形式から文書への変換 |
| L4 | `raytrace-engine`（`raytrace-app` を改名・再編） | セッション、コマンド、計算パイプライン、走査・収束確認 |
| L5 | `raytrace-gui`、`raytrace-mcp`（新設）、`raytrace-cli`、Web版のフロントエンド（新設） | 薄いフロントエンド |
| 道具 | `xtask` | 層とWASMの検査など、開発用の作業。製品には含めない |

## 5. ドメインモデル（設計文書）

### 部品と配置の木

文書は **部品（component）と配置（occurrence）の木** です。単体のZMXも「部品が1つの文書」として同じ形で表します。

```
Design（文書）
├─ environment   単位・波長・基準媒質・追跡の設定
├─ components    部品の定義（それぞれ自分の局所座標で書く）
│   ├─ 光学部品   面・NSCオブジェクト・材料（ZMX由来や手入力）
│   ├─ 光源       発光の定義（Source Diode など）
│   ├─ 検出器     スクリーンの寸法と画素
│   └─ 形状部品   ロッドなど、寸法から面を生成する部品
├─ root          ルート部品。配置の一覧を持つ
│   └─ occurrence  部品の参照＋剛体変換（位置・回転）＋有効/無効
├─ analyses      保存しておく解析の定義（スクリーン、走査計画など）
└─ provenance    取り込み元（ファイル名・ハッシュ・原文の保管場所）
```

- **同じ部品を複数配置できます。** 定義を直すと、すべての配置に反映されます。
- **部品は入れ子にできます。** 光源とレンズを1つのユニットにまとめる、といった使い方です。
- **参照は安定したIDで行います。** 面番号や配列の添字では参照しません。エージェントが編集しても参照が崩れないようにするためです。
- **元のZMXは出所として保管します。** 計算に使う形とは分けて持ちます。

### 展開（コンパイル）

`compile(Design) -> (CompiledScene, Diagnostics)` は純粋な関数です。配置の変換を合成して全体座標の面・材料表・光源・検出器の一覧にし、検証と正規化を行います。計算核は `CompiledScene` だけを知り、文書の木を知りません。結果は文書の内容ハッシュで再利用できます。

### 文書の規則（段階2で確定）

| 項目 | 規則 |
|---|---|
| 型 | L2の `raytrace-doc` に `Design`（文書）・`Part`（部品）・`Occurrence`（配置）を置く。`Project` はなくす |
| ID | 部品と配置は文書内で一意の文字列ID（`[a-z][a-z0-9_-]*`）を持つ。新しいIDは `<種類>-<番号>`（`optic-3` など）で作り、番号は文書の `next_id` から払い出して再利用しない。面は「配置ID＋面の名前」で参照する（面の名前は部品の中で一意であることを既に検証している） |
| 部品の種類 | `system`（追跡方式・光源・検出器を含む完結した光学系）、`source`、`optic`、`rod`、`detector` |
| 部品の中身 | 局所座標の面・材料表と材料名・光源、取り込みの問題点、条件（未コート、単色波長）、CAD分割精度、出所 |
| 階層 | 型は入れ子を表せる形にするが、段階2で扱うのはルート直下の配置だけ |
| 展開の規則 | 配置が1つだけで、それが `system` 部品の恒等配置（移動・回転なし）のときは、部品をそのまま光学系とする。面の名前・材料表・問題点・追跡方式を変えない（単独の完結系は組み立てない）。それ以外は非逐次の組立として合成する（面の名前に配置の番号と名前を付け、材料表を統合し、光源と瞳を配置の変換で動かす）。逐次の追跡は前者の場合だけ |
| 恒等配置 | 移動・回転のない配置は座標を変換しない。変換で丸め誤差を入れないため |
| 出所 | 元のZMXなどは、形式名とJSON値として不透明に保管する。L2は中身を解釈せず、L3の入出力が型に変換して使う（ZMXの書出しなど） |
| 保存形式 | `raytrace-design-v1`。読み込みでは旧プロジェクト形式（v1〜v3）、光学系だけのJSON（`examples/*.json`）、旧版の計算記録・走査記録に入った旧プロジェクトを、最新の形に移行する |

### パラメーター（その先の段階）

寸法や位置を名前付きの変数と式で表せるようにします。走査の連動条件、最適化の変数、公差の摂動は、どれも「変数に値を入れて展開し直す」ことで表せます。

## 6. 現状との差

| 目指す姿 | 現状（v0.11系） |
|---|---|
| 文書が唯一の正（P1） | `Project`（元ZMXを含む）・`Scene`（編集対象でもあり計算入力でもある）・`Assembly` の役割が重なっている |
| 部品と配置の木 | 組立は部品を `Project` ごとコピーして持つ。単体のZMX・JSONは別の文書モデルで、GUIの編集方法も別 |
| 安定したID | 走査の対象などを部品番号・面番号で参照している |
| すべての操作はコマンド（P2） | 計算と読込・保存は `engine::Request` に統一済み。編集はGUIが `Project` を直接書き換え、エージェントはJSONを手で編集する |
| セッション | エンジンは一回限りの呼び出しだけで、文書を開いたまま操作できない。取り消しはGUIの中だけにある |
| 計算は1本のパイプライン（P3） | 段階1で実現済み。上書き・上限・発射の確定・追跡・記録・解析の各段が `raytrace_app::pipeline`（`crates/raytrace-app/src/pipeline.rs`）にあり、`engine/run.rs`・`scan.rs`・`convergence.rs` が共有する。`record.rs` から追跡を除いた |
| 解析は登録制（P9） | 光量比・半値幅・ROIが、エンジン・出力処理・GUIに散在している |
| 外部形式は境界で変換（P6） | 文書が元ZMXと取り込みの問題点を抱え、計算記録も文書全体を含む |
| 層の自動検査（P4） | 実現済み。`cargo xtask layers` が層の順序・GUI依存の隔離・計算核の純粋さを、`cargo xtask wasm` がL0〜L4のWASMビルドをCIで検査する |
| 落ちない（P8） | エラー型は整っているが、製品コードに `unwrap`・`expect` が残る |
| 契約はスキーマ（P5） | 実現済み。`schemas/` を生成し、古さをテストで検出している |
| 決定性（P7） | 実現済み。集計順の固定、SIMD・BVHと基準経路の一致テストがある |

## 7. セッションとコマンド

### セッション

セッションはL4にあり、次のものを持ちます。

- 開いている文書（不変の値として持ち、変更のたびに新しい版を作る）と、その版番号
- 取り消し・やり直しの履歴
- 実行中のジョブ（ID・進捗・中止）
- 展開結果や計算結果のキャッシュ（内容ハッシュで再利用）

選択状態やカメラなどの表示の状態はGUIのものとし、文書には入れません。

### コマンド

| 項目 | 規則 |
|---|---|
| ID | `<領域>.<動作>` の小文字ドット区切り（`doc.open`、`component.move`、`analysis.trace`） |
| 契約 | 入力と出力のJSONスキーマを必ず持つ。未知のフィールドは拒否 |
| 種類 | 文書を変える「変更」と、変えない「問い合わせ」に分ける |
| 変更 | 既定で取り消し可能。成功するまで文書を変えない。`expected_revision` を付ければ、GUIとエージェントが同時に編集しても古い版への上書きを拒否できる |
| まとめて実行 | 複数の変更を1つの取り消し単位として、全部成功か全部失敗で実行できる |
| 長い計算 | ジョブとして開始し、IDで進捗・中止・結果を扱う |
| 発見 | `command.list` と `command.describe` で、コマンドの一覧とスキーマを問い合わせられる |
| 対話 | プログラムからの呼び出しはダイアログを開かない |

### 最初のコマンド体系（案）

| 領域 | コマンド |
|---|---|
| `doc` | `new`、`open`、`save`、`import`（ZMX・STEP）、`export`（ZMX）、`get` |
| `component` | `add`、`remove`、`set`（寸法・材料など）、`place`（配置・変換）、`enable` |
| `source`・`detector` | `set` |
| `analysis` | `trace`、`budget`、`screen`（分布・断面・半値幅・ROI）、`compatibility` |
| `study` | `scan`、`resume`、`convergence` |
| `run` | `replay`、`open`、`save`、`export_screen` |
| `session` | `undo`、`redo`、`status`、`job.status`、`job.cancel` |
| `command` | `list`、`describe` |

現在の `engine::Request` のコマンドは、この体系へ名前を変えて移します。

## 8. 計算パイプライン

```
Design ─compile→ CompiledScene ─configure→ CompiledScene' ─prepare→ PreparedScene
                                                                         │
     解析結果 ←analyze─ Report ←accumulate─ 光線ごとの結果 ←trace─ launch ─┘
```

- 各段は純粋な関数で、入出力は型付きの成果物です。前後の段の中身を知りません。
- 単発の追跡・走査・収束確認・再計算・GUIのプレビューは、**同じ段の組み合わせ方の違い**として書きます。独自の追跡ループを持ちません。
- 走査や最適化は、文書の変数を変えて展開以降をやり直すだけです。展開結果はキャッシュで再利用します。
- 中止と進捗は外から渡す制御オブジェクトで扱います。
- 決定性の規則（P7）はこのパイプライン全体で守ります。並列化しても固定の区切りと順序で集計します。

## 9. 解析

解析は登録制の純粋関数です。

```
Analysis { id, 設定のスキーマ, 結果のスキーマ, run(CompiledScene, Report/Run, 設定) -> 結果 }
```

- 解析を登録すると、`analysis.<id>` コマンド、MCPのツール、CLIの引数、スキーマが自動で揃います。
- GUIは結果を描くだけで、計算を自分で持ちません（表示のための補間などは除きます）。
- 現在の候補は、光量収支、スクリーン分布、断面と半値幅、ROI、互換性レポートです。次の段階でスポット図、光線収差図、OPDを足します。

## 10. 入出力と形式

| 対象 | 方針 |
|---|---|
| 設計文書 | 版付きのJSON（スキーマあり）。読み込みは過去の版から最新へ移行し、書き出しは最新の版だけ。版を上げるときは移行処理とテストを同時に足す |
| 計算記録 | 計算に使った `CompiledScene`・発射条件・追跡条件・版・文書のハッシュを持つ。これだけで再計算できる。文書そのものを含めるかは選択式にする |
| 外部形式の取り込み | ZMX・AGF・STEPは部品として取り込み、出所を記録する。対応しない定義は互換性レポートで明示し、黙って捨てない |
| 書出し | ZMX、スクリーンのCSV・PNG。外部形式で表せない内容は書き出せないことを明示する |
| 利用者のデータ | ZMX・STEP・計算記録はリポジトリに含めない（既存の公開物チェックを維持） |

## 11. フロントエンド

| 入口 | 役割 |
|---|---|
| GUI | セッションの状態を読んで描き、操作はすべてコマンドで送る。ダイアログはコマンドの引数を作るだけ。描画・カメラ・選択はGUIの責任 |
| MCP | 標準入出力のJSON-RPC。窓なしでセッションを持って動く方式と、起動中のGUIにローカルの制御チャネル（そのつど作るトークン付き）でつなぐ方式を持つ。後者では、人がGUIでエージェントの操作を見られる。引数の検査は「なし・警告・拒否」を選べる |
| CLI | 窓なしのセッションの薄い殻。`raytrace-rs COMMAND field=値` と `run REQUEST.json` で、MCPと同じコマンドを1回ずつ実行する。独自のオプションは持たない |
| スキル・AGENTS.md | エージェントへの案内。コマンドの詳細はスキーマと `command.describe` を正とし、文書に重複して書かない |

## 12. 信頼性と検証

## 13. 移行計画

一度に作り直さず、新しい構造で古い部分を順に置き換えます（絞め殺しのイチジク方式）。各段階の終わりで全テストとCIが通る状態を保ちます。

| 段階 | 内容 | 完了の条件 |
|---|---|---|
| 0 | この文書を設計指針として採用する。`cargo xtask layers`（層・依存・純粋さ）と `cargo xtask wasm`（L0〜L4のWASMビルド）をCIに入れる | 違反がCIで検出される |
| 1 | 計算パイプラインを1本にする。展開〜記録の段を純粋関数として切り出し、エンジン・走査・収束確認・再計算をそれに乗せる。外部仕様は変えない | 追跡ループが1か所だけになり、既存のテストがすべて通る |
| 2 | 設計文書を部品と配置の木にし、安定したIDを導入する（`raytrace-doc`）。単体のZMXも部品1つの文書にする。過去のプロジェクト形式（v1〜v3）は読み込み時に移行する | GUIと計算が新しい文書だけを使う。旧形式のサンプルを読める |
| 3 | セッションとコマンド登録をエンジンに入れる（`raytrace-engine`）。取り消し・版番号・ジョブ・`command.describe` を持たせ、CLIをその上に載せる | `engine::Request` がコマンド体系に置き換わる |
| 4 | GUIの編集をすべてコマンド経由にする。GUIが文書を直接書き換える箇所をなくす | GUIで行った編集を、同じコマンド列で再現できる |
| 5 | MCPサーバー（`raytrace-mcp`）を足す。窓なしの方式と、GUIへ接続する方式を持つ | エージェントがGUIと同じ操作で設計・計算・解析を行える |
| 6 | 解析の登録制を広げ、検証を体系化する。製品コードから `unwrap`・`expect` をなくす | 解析を足すときに中核以外を変えずに済む |
| 7 | Web版。L4のセッションをブラウザで動かし、WASM向けのフロントエンドから同じコマンドを使う。スレッドなしでも同じ結果になることをテストする | ブラウザでサンプルを開いて追跡・表示できる |
| 8以降 | 逐次系の標準解析、パラメーターと最適化、公差解析、回折・偏光 | [1章](#機能の到達範囲) の段階に従う |

## 16. 用語

| 用語 | 意味 |
|---|---|
| 文書（設計文書） | 光学系の唯一の正。部品・配置・環境・解析の定義・出所を持つ |
| 部品（component） | 局所座標で定義された光学系の単位。レンズ、光源、検出器、ロッドなど |
| 配置（occurrence） | 部品の参照と剛体変換。同じ部品を複数配置できる |
| 展開（compile） | 文書を全体座標の面の一覧（`CompiledScene`）に変換する純粋な処理 |
| コマンド | セッションに対する名前付きの操作。入出力のスキーマを持つ |
| セッション | 開いた文書・履歴・ジョブ・キャッシュを持つエンジンの状態 |
| 計算記録 | 1回の追跡の条件と結果。単独で再計算できる |
| 解析 | 展開結果と追跡結果から結果を計算する、登録制の純粋関数 |
